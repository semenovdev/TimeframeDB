# TimeframeDB — архитектура и направление исследований

> **Статус:** Первоначальное предложение по архитектуре (17 октября 2026 года)  
> **Проект:** TimeframeDB  
> **Предполагаемая модель:** Открытый исходный код, исследовательский подход, совместимость с Unix  
> **Содержание документа:** Архитектурные решения, границы проекта, проектные гипотезы и план проверки. Это не окончательная спецификация формата хранения или API.

## 1. Видение

**TimeframeDB** — экспериментальная легковесная база данных временных рядов, ориентированная на добавление записей, эффективную пакетную загрузку, сканирование временных диапазонов и агрегацию по таймфреймам.


### Принципы проектирования

- **Корректность важнее результатов бенчмарков.** Семантика надёжного сохранения данных, видимости и времени должна быть явно определена и поддаваться проверке.
- **Инженерные цели важнее приверженности языку.** Предпочтение отдаётся реализации, которая отвечает требованиям к корректности, производительности и удобству сопровождения; Rust — основной язык движка, а Haskell предоставляет выразительную среду для языка запросов.
- **Понятное внутреннее устройство.** Предпочтение отдаётся небольшой кодовой базе и объяснимым алгоритмам, а не широкому набору возможностей.
- **Композиция в духе Unix.** Создавать самостоятельно полезные программы, взаимодействующие через чётко определённые потоки и протоколы.
- **Стандарты там, где они уместны.** Исследовать новые алгоритмы хранения и агрегации, но для совместимости использовать существующие стандарты, а не изобретать новые форматы табличных результатов.
- **Оптимизация на основе данных.** Сравнивать производительность реальных реализаций, измерять потребление ресурсов и сохранять отрицательные результаты.

## 2. Начальная рабочая нагрузка

Основная нагрузка состоит из событий с временными метками, которые преимущественно добавляются в базу, например биржевых тиков или сделок. Данные финансовых рынков служат мотивирующим примером, **но не** ограничивают предметную область базы данных навсегда.

| Операция | Приоритет | Примечания |
| --- | --- | --- |
| Согласованное пакетное добавление | Обязательно | Основная единица записи — пакет, а не вставка отдельной строки. |
| Сканирование диапазона по времени события | Обязательно | Эффективный последовательный или пакетный доступ к временным интервалам. |
| Агрегация по таймфреймам | Обязательно | Временные корзины и агрегация наподобие OHLCV там, где это допускает схема. |
| Согласованная инкрементальная синхронизация | Обязательно | Отслеживать прогресс источника, избегать случайных дубликатов, восстанавливаться после сбоев. |
| Потоковая выдача результатов пакетами | Обязательно | Не загружать весь набор результатов в память перед выдачей. |
| Поиск конкретной записи | Низкий приоритет | Не является целью оптимизации. |
| Обновления, удаления, произвольные соединения | За рамками начальной версии | Вернуться к ним только при наличии убедительной рабочей нагрузки. |
| Универсальная поддержка SQL | За рамками начальной версии | Позже можно добавить ограниченный интерфейс, похожий на SQL. |

Начальная модель выполнения может предполагать **одного писателя и нескольких читателей**. Гарантии параллельного доступа и надёжного сохранения данных всё равно необходимо определить и проверить.

## 3. Архитектура процессов

TimeframeDB намеренно разделяет интерфейс запросов и движок выполнения на независимые процессы операционной системы.

```text
                 Приложение на Haskell / CLI
             +----------------------------------+
             | Типизированный DSL запросов      |
             | (позже: парсер, похожий на SQL)  |
             | AST + семантические проверки     |
             | Логическое представление запроса |
             +----------------+-----------------+
                              |
                   версионированный протокол запросов
                              |  stdin / канал / IPC
                              v
             +----------------------------------+
             | Движок TimeframeDB на Rust       |
             |----------------------------------|
             | Проверка плана                   |
             | Физическое выполнение            |
             | Пакетная запись / сканирование   |
             | Агрегация по таймфреймам         |
             | Хранилище / индекс / фиксация    |
             +----------------+-----------------+
                              |
                       Arrow IPC Stream
                              |  stdout / канал / IPC
                              v
         +----------------------------------------------+
         | Клиенты: Haskell, Go, Java, Kotlin, C, Rust  |
         | и другие языки с поддержкой Arrow            |
         | CLI, преобразования, коннекторы              |
         +----------------------------------------------+
```

### Принятые решения

1. **За хранение и выполнение отвечает Rust.** Движок управляет файлами, индексами, транзакциями и фиксацией изменений, физическим планированием запросов, сканированием и агрегацией.
2. **За первый интерфейс запросов отвечает Haskell.** Первым интерфейсом станет типизированный DSL на Haskell, строящий логическое представление запроса. Позже ограниченный парсер, похожий на SQL, сможет использовать ту же семантическую модель.
3. **На основном пути не нужен FFI между Rust и Haskell.** Границей служит явный протокол, а не общие нативные указатели или общая куча.
4. **Haskell не обязателен как посредник при выдаче результатов.** Потребители могут читать вывод движка на Rust напрямую; CLI на Haskell — лишь один из возможных потребителей.
5. **Rust обязан самостоятельно проверять входящие планы.** План, полученный от любого клиента, считается недоверенным вводом, даже если интерфейс на Haskell уже проверил его.

Компоненты должны оставаться пригодными к независимому использованию. До появления DSL на Haskell движком можно управлять с помощью тестовых планов, составленных вручную.

## 4. Интерфейсы запросов и логические планы

### Этап 1: нативный DSL на Haskell

Первый интерфейс — библиотека для построения типизированных запросов. Она должна предоставлять, в частности, следующие операции:

- Выбор источника данных и необязательного раздела или инструмента.
- Ограничение диапазона по времени события.
- Чтение исходных событий пакетами.
- Агрегация по поддерживаемым таймфреймам.
- Выбор полей или форматирование поддерживаемых форматов вывода.

Точный синтаксис ещё не выбран. Ниже приведён **иллюстративный псевдокод**, а не обещанный API:

```haskell
query =
  from "trades"
    |> symbol "BTCUSDT"
    |> between start end
    |> ohlcv Minutes5
```

### Этап 2: интерфейс, похожий на SQL

На Haskell можно реализовать намеренно ограниченный парсер, похожий на SQL, который компилирует запросы в **те же типизированное AST и логическое промежуточное представление запроса (Query IR)**. Ему не нужно генерировать исходный код на Haskell или реализовывать общую семантику SQL.

```text
DSL на Haskell ----------+
                        +--> общее AST --> семантический анализ --> Query IR
Парсер, похожий на SQL --+
```

Движок сопоставляет проверенные логические операции с физическими алгоритмами с учётом доступных индексов, сегментов и заранее вычисленных агрегатов. Интерфейсы запросов не должны зависеть от формата хранения на диске.

### Протокол запросов: ещё не выбран

Query IR — **отдельный протокол**, отличный от потоковой выдачи результатов в Arrow. Его начальное представление, схема и способ разграничения сообщений при передаче ещё предстоит выбрать. Читаемый версионированный формат (например, JSON) может быть полезен при разработке и создании тестовых данных, но это **пока не принятое решение**.

Обязательные свойства:

- Явные идентификаторы протокола и версии.
- Однозначная семантика временных диапазонов, границ корзин, типов и порядка.
- Строгие ограничения длины и ресурсов, проверка входных данных и понятные ошибки с указанием дальнейших действий.
- Возможность сохранить и воспроизвести план независимо от интерфейса запросов.
- Возможность проверять совместимость по мере развития интерфейса и движка.

## 5. Результаты и совместимость

**Решение: использовать Apache Arrow IPC Stream для табличных результатов запросов.**

- Rust выдаёт схему, а затем последовательные пакеты записей Arrow.
- Потребители могут быть написаны на Haskell, Go, Java, Kotlin, C, Rust или другом языке с совместимым средством чтения Arrow IPC.
- Потоки результатов должны поддерживать потребление с ограниченным объёмом памяти и обратное давление.
- Arrow — **формат результатов для обмена между процессами**, а не обязательный формат хранения на диске.
- Для управляющих сообщений запроса, состояния выполнения и передачи ошибок после начала потока нужны явные соглашения сверх возможностей самого Arrow.

Обычные каналы Unix подходят для начального транспорта. Они передают потоки байтов, поэтому границы сообщений задаются выбранным протоколом. Для долговременных артефактов можно явно выбрать совместимое представление файла или потока Arrow. Не следует называть произвольный набор байтов файлом Arrow, если он не соответствует формату Arrow.

Иллюстративный конвейер (команды **не реализованы**):

```sh
timeframedb-query compile query.hs \
  | timeframedb-engine execute \
  | timeframedb-output table
```

Стандартный вывод должен содержать только предназначенный для машинного чтения поток; журналы и диагностические сообщения следует направлять в стандартный поток ошибок. Потребители и запускающие программы должны обнаруживать разрыв канала, ненулевой код завершения процесса и неполные результаты. Поток, завершившийся с ошибкой, не должен незаметно считаться успешно выданным полным результатом.

Для больших результатов **потоковая обработка и ограниченный объём памяти обязательны; сквозное отсутствие копирования — нет**. Копирование всё равно может происходить при межпроцессном обмене через ядро и декодировании формата. Следует избегать ненужных преобразований и загрузки всего результата в память.

## 6. Архитектура хранения: исследовательские гипотезы

Физический формат хранения **ещё не** выбран. Основной кандидат — архитектура, ориентированная на добавление записей, с неизменяемыми сегментами, хронологическими метаданными, разреженными временными индексами и необязательными инкрементальными агрегатами.

```text
appendBatch(events)
      |
      v
проверка / политика устранения дубликатов
      |
      v
неизменяемые сегменты + метаданные
      |
      +----> разреженный временной индекс
      +----> необязательные сводные агрегаты / иерархия таймфреймов
      |
      v
атомарная публикация новой версии, доступной для чтения
      |
      v
сканирование диапазона / агрегация / пакеты записей Arrow
```

Кандидаты для изучения и измерения производительности:

1. **Эталон по мотивам DuckDB:** колоночные группы строк, карты зон по минимуму и максимуму, пакетное векторизованное сканирование и агрегация.
2. **Сегменты, ориентированные на добавление:** независимо читаемые неизменяемые файлы с компактным временным индексом.
3. **Структуры для агрегации:** сводки для фиксированных таймфреймов, иерархические агрегаты или дерево агрегатов, если оно оправданно.
4. **Кодирование и сжатие:** исходные столбцы фиксированной ширины, временные метки с дельта-кодированием, сжатие и стоимость декодирования.
5. **Способы чтения:** буферизованный последовательный ввод-вывод и отображение файлов в память; выбор по результатам измерений.

Реализация по мотивам DuckDB **не равнозначна самой DuckDB**. Настоящая база данных с зафиксированной версией и контролируемой конфигурацией остаётся отдельной базой для сравнения.

### Агрегация по таймфреймам

Для упорядоченных непустых диапазонов событий агрегаты OHLCV можно объединять следующим образом:

```text
combine(A, B):
    open   = A.open
    high   = max(A.high, B.high)
    low    = min(A.low, B.low)
    close  = B.close
    volume = A.volume + B.volume
```

Реализация должна определить нейтральный элемент для пустого диапазона, однозначный порядок событий (в том числе при одинаковых временных метках), поведение при числовом переполнении и границы корзин. При соблюдении этих соглашений операция объединения ассоциативна, что позволяет агрегировать сводки вместо повторного сканирования всех исходных событий.

**Гипотеза, а не утверждение о производительности:** индексированные, заранее вычисленные агрегаты по таймфреймам могут ускорить повторяющиеся запросы агрегации. Для честного сравнения их нужно сопоставлять с **DuckDB с аналогично материализованными сводками**, а не только с DuckDB, повторно сканирующей исходные тики.

## 7. Согласованное добавление и инкрементальная синхронизация

Для синхронизации «по дате» недостаточно запоминать наибольшую сохранённую временную метку.

В проекте необходимо различать:

- **Время события:** когда событие действительно произошло.
- **Курсор источника / контрольная точка:** подтверждённый прогресс в порядке выдачи или протоколе постраничной загрузки источника.
- **Отметка полноты:** до какого времени событий источник позволяет обоснованно считать данные полными.

Связь между ними зависит от гарантий источника. В частности, `MAX(event_time)` нельзя автоматически считать границей полной синхронизации.

### Обязательные свойства

- Атомарная видимость зафиксированного пакета: читатели никогда не видят частично зафиксированный пакет.
- Надёжное сохранение фиксаций и возможность восстановления в рамках явно определённой модели отказов.
- Определённая стратегия обработки повторных попыток, повторно переданных пакетов и идентичности дубликатов.
- Согласованные снимки для читателей во время добавления данных писателем.
- Тесты восстановления после прерываний при записи данных и публикации метаданных.
- Явная обработка или отклонение запоздавших событий и событий, поступивших не по порядку, в начальной версии.

Возможный подход — записывать неизменяемые сегменты, обеспечивать надёжное сохранение их данных, а затем атомарно публиковать новый манифест с видимым набором сегментов и контрольной точкой источника. Это пока **вариант проекта**, а не проверенный протокол. До заявлений о надёжном сохранении данных необходимо определить и проверить атомарную замену, синхронизацию каталогов, семантику файловых систем на разных платформах, очистку незафиксированных файлов и восстановление после сбоев.

Один писатель при нескольких читателях и монотонный порядок добавления — разумные упрощения для начальной версии. Исправления исторических данных, запоздавшие события, параллельных писателей и распределённую репликацию можно исследовать позже.

## 8. Модель потребления ресурсов и эксплуатации

Одна из главных целей — **небольшое и предсказуемое потребление ресурсов**, особенно по сравнению с эксплуатационными потребностями полноценного стека PostgreSQL/TimescaleDB. Проект должен явно учитывать накладные расходы на индексы, использование кучи, нагрузку на страничный кеш, время запуска и усиление записи.

Разделение Rust и Haskell на независимые процессы позволяет применять к ним разные политики операционной системы:

| Область политики | Движок на Rust | Интерфейс запросов / средство вывода на Haskell |
| --- | --- | --- |
| ЦП | При обоснованной необходимости отдавать предпочтение движку выполнения в условиях конкуренции за ресурсы | Снижать вес фоновой работы, но не лишать ресурсов подготовку запросов, для которой важна задержка |
| Память | Измерять и защищать подходящий рабочий набор | При необходимости ограничивать память фонового или кратковременно работающего интерфейса |
| Ввод-вывод | При необходимости отдавать приоритет критичным для хранилища операциям ввода-вывода | Разные политики для интерактивных и фоновых инструментов |
| Жизненный цикл | Может работать как сервис или однократно запускаемая CLI-программа | Может запускаться по требованию |

Для развёртывания в Linux следует исследовать systemd и cgroups v2 (`CPUWeight`, `MemoryLow`, `MemoryHigh`, `MemoryMax` и применимые средства управления вводом-выводом). Это **политики развёртывания, а не встроенные настройки движка по умолчанию**. Вес ЦП задаёт относительный приоритет, а не зарезервированное процессорное время; защита памяти не гарантирует закрепления выделенной памяти. Раздельные процессы не означают автоматически раздельные cgroups.

Важный эксплуатационный тест — конкуренция за ресурсы: нужно измерять задержку и пропускную способность, когда посторонняя нагрузка на ЦП, память и диск конкурирует с движком. Чрезмерный приоритет Rust может навредить, если недостаток ресурсов у производителя запросов или потребителя результатов блокирует весь конвейер.

Планирование в реальном времени не является требованием по умолчанию.

## 9. Стратегия исследований и бенчмарков

На начальном этапе будут сравниваться алгоритмы, прежде чем делать сильные архитектурные утверждения.

| Вариант | Назначение |
| --- | --- |
| Настоящая DuckDB | Внешняя база промышленного уровня для сравнения с явно указанной версией и справедливой, настроенной конфигурацией. |
| Эталонная реализация приёмов DuckDB на C | Выделить и понять отдельные алгоритмы колоночного хранения, карт зон и векторизованной обработки. |
| Эталонная реализация тех же приёмов на Rust | Учесть влияние языка реализации и изучить устройство движка хранения на Rust. |
| Специализированный движок на Rust, ориентированный на добавление | Проверить преимущества и издержки более узких стратегий хранения и индексации. |
| DuckDB с заранее вычисленными агрегатами | Справедливая база для сравнения повторяющихся запросов по таймфреймам. |


### Группы бенчмарков

- Пакетная загрузка при разных размерах пакета.
- Сканирование узких и широких временных диапазонов.
- Агрегация исходных событий по таймфреймам разных размеров.
- Повторное чтение уже вычисленных агрегированных данных.
- Один источник данных по сравнению с несколькими символами или разделами.
- Инкрементальная синхронизация, перекрывающиеся и повторно переданные пакеты, восстановление после сбоя.
- Параллельное добавление данных и чтение снимков.
- Конкуренция за ресурсы и условия с холодным или прогретым кешем.

### Метрики

Пропускная способность (событий/с), задержка (в том числе p50/p95/p99, где уместно), пиковый RSS, использование кучи и аллокатора, загрузка ЦП, число прочитанных и записанных байтов, ошибки страниц, число байтов индекса на байт исходных данных, общий объём хранимых данных, усиление записи, время запуска и время восстановления.

Все реализации должны использовать эквивалентную семантику и выдавать результаты, совпадающие с эталонными. Не следует сравнивать небезопасное добавление без сброса данных на диск с надёжно сохраняемой фиксацией так, будто они дают одинаковые гарантии. Эксперименты с алгоритмами в памяти нужно отделять от экспериментов с базой данных на диске, а стоимость первоначального построения — от стоимости запросов.

## 10. Что не входит в цели первой версии

- Универсальная база данных с SQL или полная совместимость с PostgreSQL.
- Оптимизация точечного поиска по отдельным строкам или обязательное B-дерево для каждого столбца.
- Распределённая координация, шардирование, консенсус или репликация.
- Полная поддержка произвольных обновлений, удалений, соединений и пользовательских функций.
- Собственный межъязыковой протокол для колоночных результатов.
- Встраивание GHC в процесс Rust или требование использовать FFI между Rust и Haskell.
- Демонстрация превосходства над DuckDB на всех нагрузках.

## 11. Предлагаемые этапы

1. **Аудит архитектуры:** изучить реальные механизмы хранения, векторизации, агрегации и надёжного сохранения данных в DuckDB; зафиксировать источники и версии.
2. **Спецификация нагрузки и корректности:** определить схемы событий, семантику таймфреймов, пакетную обработку, контрольные точки источника и необходимые гарантии.
3. **Эталонные эксперименты:** реализовать минимальные алгоритмы по мотивам DuckDB на C и Rust и сравнить их с настоящим движком DuckDB.
4. **Прототип хранилища на Rust:** реализовать добавление, обнаружение сегментов, сканирование временных диапазонов, базовую агрегацию и тесты корректности.
5. **DSL на Haskell + Query IR:** создать типизированный интерфейс запросов и управлять движком Rust через версионированный контракт планов.
6. **Интеграция Arrow IPC:** передавать пакеты записей независимым потребителям, при необходимости включая CLI для вывода на Haskell.
7. **Согласованность и восстановление:** укрепить фиксацию пакетов, идемпотентную синхронизацию, семантику снимков и тестирование сбоев.
8. **Специализированные структуры:** добавлять разреженные индексы, материализацию агрегатов и сжатие по отдельности, руководствуясь бенчмарками.
9. **Необязательный парсер, похожий на SQL, и коннекторы:** держать их отдельно от ядра движка.
10. **Отчёт об исследованиях:** опубликовать воспроизводимые измерения, отрицательные результаты, инженерные компромиссы и ограничения.
